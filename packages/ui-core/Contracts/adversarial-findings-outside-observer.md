# Adversarial Review — Outside Observer Perspective
Date: 2026-06-05

## Summary

A new team member can implement most M1-phase components (those with all 4 contracts) from the contracts alone. However, the M1 short-form contracts, all DataVisualization/AI/Scheduling forward-specs, and cross-component references use unexplained jargon, dangling type references, and implicit conventions that would force a new implementor to go hunting. Seventeen findings are catalogued below.

---

## Findings

| Finding ID | Severity | Component(s) | Description | Suggested Fix |
|---|---|---|---|---|
| OO-1 | High | All M1 short-form Semantic contracts (ComboBox, DatePicker, Breadcrumb, Editor, CommandPalette, etc.) | **Header format inconsistency — M1 files strip the full header template.** M2 files (Button, Notification, TextField, StatusBanner) have a rich header with `Status`, `Companion contracts`, `Reference implementation`, `Catalog row`, `Phase`, `Foundation`. M1 short-form files carry the same fields but omit the `Foundation` field entirely and have no `Definition of Done` gate table. A new implementor has no idea what base library to start from (shadcn? Radix? headless?) for M1 components. | Add a `Foundation:` field to every M1 header, even if it reads "none — hand-rolled" or "Radix Combobox". Add a `Definition of Done` table to every Semantic contract regardless of phase. |
| OO-2 | High | BarChart, ColumnChart, RadarAreaChart, RadarColumnChart, and all other chart Semantic contracts | **Cross-file type reference with no link and no inline definition.** `BarChart.Semantic.md §2` references `ChartDataPoint[]` with the annotation `// see AreaChart.Semantic.md for ChartDataPoint`. `ColumnChart.Semantic.md §2` extends `Omit<BarChartProps, 'layout'>` with `// Inherits all props from BarChartProps. See BarChart.Semantic.md`. These are unlinked prose references — a new team member has no hyperlink, no inline fallback, and no guarantee the type hasn't changed in the source file. The same pattern appears in LinearGauge referencing `GaugeScale` from `CircularGauge.Semantic.md`. | Replace inline comments with Markdown links: `[ChartDataPoint](./AreaChart.Semantic.md)`. For `extends` relationships, either inline the full extended interface **or** provide a clearly labelled link. |
| OO-3 | High | RadialGauge | **"Same interface as CircularGaugeProps" — no link, no inline copy.** `RadialGauge.Semantic.md §2` says "Same interface as `CircularGaugeProps`. See `CircularGauge.Semantic.md`." without linking. The section heading is `## 2. Props (planned)` but contains no TypeScript — only prose. An implementor must navigate manually. | Replace with a Markdown link to `CircularGauge.Semantic.md` and list the key distinctions in a props-delta table rather than prose. |
| OO-4 | High | ComboBox (and by implication all M1 components with known gaps) | **Known gaps listed in Interaction but not forwarded to Accessibility (and vice versa).** `ComboBox.Interaction.md` lists G-CBX1 through G-CBX4. `ComboBox.Accessibility.md` lists G-CBX1 through G-CBX3 and then **G-CBX5, G-CBX6** — the gap IDs skip G-CBX4 and the numbering diverges between the two files. A new implementor using only the Accessibility contract misses G-CBX4 (`allowCustom` silently ignored) and vice versa for G-CBX5/G-CBX6. | Maintain a single canonical "Known Gaps" table in the Semantic or Interaction contract, and make Accessibility point to it with a link. Do not maintain parallel (and divergent) tables in two contracts for the same component. |
| OO-5 | High | InlineAIPrompt | **Cross-reference to `AIPromptOutput` with no link and no inline definition.** `InlineAIPrompt.Semantic.md §2` references `AIPromptOutput` in the interface but says only "`AIPromptOutput` is identical to AIPrompt Semantic §2." A new implementor must navigate to `AIPrompt.Semantic.md`, locate `§2`, and manually extract the type. No Markdown link is provided. | Add a direct link: `[AIPromptOutput](./AIPrompt.Semantic.md)`. Consider inlining the type since it is short. |
| OO-6 | Medium | All 7 out-of-scope Utility stubs (AnimationContainer, DataQuery, DateMath, Diagram, ExcelExport, FileSaver, KeyboardNavigation, MediaQuery, Ripple) | **Stubs lack a "use this instead" section with a link or package name.** AnimationContainer says "use Framer Motion or CSS `@keyframes` at the application layer" — good. DataQuery says "use TanStack Table" — good. But `DateMath`, `ExcelExport`, `MediaQuery`, and `Ripple` stubs are not listed in the directory output (not read), while the ones read vary in how explicitly they name alternatives. The quality is inconsistent: some stubs name exact npm packages; others name only a concept. | Adopt a uniform stub template: `## Use Instead` section with (a) the recommended npm package or internal hook with an exact name, (b) one sentence on why this component is not in scope, (c) a link to the relevant ADR section. |
| OO-7 | Medium | Sonner vs Notification | **Two distinct toast APIs exist with no disambiguation page or canonical choice.** `Notification.Semantic.md` (catalog #89, `app-priority: high`) and `Sonner.Semantic.md` (catalog #A6, `app-priority: medium`) both implement toast queuing with nearly identical `NotificationOptions` / `ToastOptions` shapes. Notification's contract says "Foundation: shadcn Sonner (preferred) — wrapping `sonner` library". Sonner's contract header says it is "Distinct from `Notification` (#89)" but the stated distinction (Sonner manages a queue; Notification is a single instance) contradicts Notification's own §3.5 which describes FIFO eviction and a `max` prop. A new team member will not know which to use. | Add an explicit disambiguation section to both contracts. Either (a) retire Sonner as a standalone contract and absorb it into Notification's §8 as an implementation note, or (b) document the exact use-case split with a decision rule ("Use Notification unless you need direct `sonner` token access or Sonner-specific props not exposed through Notification's API"). |
| OO-8 | Medium | ButtonGroup, ToggleButton, SegmentedControl (alias stubs) | **Alias stubs reference ToggleGroup but ToggleGroup has no "Aliases" section.** The three alias stubs say "All contracts are defined in the ToggleGroup contract family" but `ToggleGroup.Semantic.md` does not have a `## Aliases` or `## Known-as` section. A team member reading ToggleGroup would not know these aliases exist, which matters for finding the right component by search and for migration from Telerik naming. | Add an `## Aliases` section to `ToggleGroup.Semantic.md` listing `ButtonGroup`, `ToggleButton`, `SegmentedControl` with brief rationale for each alias and a link back to each stub file. |
| OO-9 | Medium | All DataVisualization chart Semantic contracts | **`hsl(var(--chart-N))` token series referenced without explanation.** `SankeyChart.Semantic.md §5` and implicitly all chart components use `hsl(var(--chart-N))`. There is no explanation of how many `--chart-N` variables exist, where they are defined, or what `N` ranges from. A new implementor must guess. The same `hsl(var(--primary))` and `hsl(var(--muted))` tokens appear in `ArcGauge.Semantic.md` without a token glossary reference. | Add a reference to the token file or section where `--chart-N`, `--primary`, and `--muted` are defined. Until that file exists, at minimum add an inline note "see `_shared/design/tokens/chart.tokens.json` (planned)" so the implementor knows where to look. |
| OO-10 | Medium | DatePicker | **`DateInputProps` referenced via `extends` with no link.** `DatePicker.Semantic.md §2` shows `interface DatePickerProps extends DateInputProps` — but `DateInputProps` is not defined in this file and no link to `DateInput.Semantic.md` is provided. An implementor must know to look there; they have no hyperlink. | Add a linked reference: `interface DatePickerProps extends DateInputProps` + inline comment `// see [DateInput.Semantic.md](./DateInput.Semantic.md)`. |
| OO-11 | Medium | ComboBox | **`fillMode` and `rounded` props have no variant semantics explained.** `ComboBox.Semantic.md §2` lists `fillMode?: 'solid' | 'outline' | 'flat'` and `rounded?: 'small' | 'medium' | 'large' | 'full'` but there is no §3 explanation of what these mean visually or structurally. A new implementor has the type but not the design intent. This contrasts sharply with Button's `variant` table (§3.2) which explains each variant's intent and typical use. | Add a "Prop semantics and defaults" table (matching Button's §3) covering at minimum `fillMode`, `rounded`, and `size` with intent descriptions. |
| OO-12 | Medium | StatusBanner | **Header format is non-conformant with all other contracts.** `StatusBanner.Semantic.md` uses a prose-style top section (`ADR: 0017-A1`, `Family: Feedback`, `Status: Accepted`) instead of the standard bullet-list header with `- **Component:**`, `- **Companion contracts:**`, etc. A toolchain or documentation generator that parses headers will fail to parse this file consistently with the other 600+ contracts. | Reformat the header to use the standard bullet-list template consistent with Button, ComboBox, Notification, etc. |
| OO-13 | Medium | Scheduler | **`step`, `startTime`, `endTime` interact but the interaction is unexplained.** `Scheduler.Semantic.md §2` lists `step?: number` (slot duration in minutes), `startTime?: string` (HH:mm), and `endTime?: string` (HH:mm) but there is no explanation of how they combine. What happens when `step=60` but `startTime='08:00'` and `endTime='17:00'`? Is the last slot trimmed or dropped? Does `endTime='24:00'` mean midnight? | Add a §3 (or subsection of §2) documenting how the time-range props compose, with an example: "A `step=30` scheduler from `startTime='08:00'` to `endTime='17:00'` renders 18 time slots." |
| OO-14 | Low | All M1 Interaction contracts with "Known Gaps" tables | **Gap dispositions are opaque — "Accepted-risk M1" has no definition.** Across ComboBox, DatePicker, CommandPalette, and others, the gap disposition column contains `Accepted-risk M1`. A new team member does not know what this means: does it mean the gap will be fixed in M2? Is it permanent? Who accepted the risk? Is there a tracking issue? | Add a one-paragraph "Gap Disposition Legend" either in each contract's Known Gaps section header or in a shared conventions file linked from every contract's References section. Define: `Accepted-risk M1` = will be addressed in M2 unless council rules otherwise; `Permanent` = intentional omission; `Tracking: #N` = GitHub issue for resolution. |
| OO-15 | Low | All forward-spec Semantic contracts (Button, Notification, CircularGauge, AIPrompt, Chat, etc.) | **"Forward-spec" term is used but never defined in any contract.** Every forward-spec contract says "This is a forward-spec: [component] has not yet been implemented." But no contract explains what the phased spec model (M1 / M2 / M4) means or where that system is documented. A new team member has no roadmap for when each phase delivers. | Add a single sentence with a link to ADR 0017-A1 in every forward-spec contract's §1 Purpose, e.g., "See ADR 0017-A1 for the M1/M2/M4 phased-spec model." |
| OO-16 | Low | Gantt | **`GanttTask.dependencies` is an array of task IDs with no explanation of the graph model.** `Gantt.Semantic.md §2` shows `dependencies?: string[]` — "array of task IDs this task depends on" — but §5 says "finish-to-start dependency arrows are drawn." A new implementor does not know: (a) are circular dependencies silently ignored or an error? (b) what happens if a dependency ID references a non-existent task? (c) is it finish-to-start only, or will other dependency types be supported? | Add a §6 "Dependency model" to Gantt.Semantic.md documenting the relationship type (finish-to-start), error handling for unknown IDs (ignored vs warning), and circular dependency behaviour. |
| OO-17 | Low | All DataVisualization Interaction contracts (not read in detail but pattern established by AreaChart, BarChart, etc.) | **`tooltip?: boolean` is specified without describing the tooltip's content model.** Multiple chart contracts declare `tooltip?: boolean` (AreaChart, BarChart, SankeyChart, etc.) but none describe what a tooltip shows: the series name? the raw value? the formatted value? whether it's customizable? A new team member will implement the feature but produce incompatible tooltip formats across chart types. | Add a "Tooltip content model" subsection (1–3 sentences) to each chart's Semantic contract describing the default content (e.g., "Series name + formatted value at the hovered data point") and whether a custom tooltip renderer prop is planned. |

- **DataEntry (7):** Button (all 4 contracts), ComboBox (Semantic + Interaction + Accessibility), DatePicker (Semantic + Interaction), Editor (Semantic), TextField (Semantic), ButtonGroup/ToggleButton/SegmentedControl/RichTextEditor (alias stubs)

- **Scheduling (3):** Scheduler, Gantt, TaskBoard (all Semantic)
- **Utility (6):** AnimationContainer, DataQuery, Diagram, FileSaver, KeyboardNavigation, Tour (all Semantic stubs)
