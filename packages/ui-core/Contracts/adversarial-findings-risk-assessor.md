# Adversarial Review — Pessimistic Risk Assessor Perspective
Date: 2026-06-05

## Summary

This review surfaces spec gaps that would produce production bugs or accessibility failures if the contracts are implemented exactly as written. The highest-risk cluster is DatePicker/DateInput, where two High-severity gaps are marked "Accepted-risk M1" but the stated alternatives provide no actual coverage for keyboard-only users. A secondary cluster is Upload + MultiSelect, where missing live-region and keyboard-navigation specs would make core workflows inoperable for screen-reader users.

---

## Findings

| Finding ID | Severity | Component(s) | Description | Suggested Fix |
|---|---|---|---|---|
| RA-1 | High | DatePicker | G-DP1 (no calendar keyboard navigation) is marked "Accepted-risk M1" with no stated alternative path for keyboard-only users. A keyboard-only user can open the calendar popover but cannot select a date — they must close it and type in the DateInput. The DateInput itself (G-DI2) does not emit `aria-invalid`, so error state cannot be communicated to AT via the text entry path either. Together, the two accepted gaps leave keyboard-only users with zero error-state feedback and no way to navigate the calendar. The "Accepted-risk M1" disposition names no compensating mechanism. | Add an explicit compensating statement to the DatePicker Interaction §5 knowledge note: keyboard-only users MUST be able to set a value via the text DateInput alone, AND the DateInput must emit `aria-invalid` (fix G-DI2 before shipping DatePicker to production) or DatePicker must surface its own `aria-invalid` on the wrapper. Fix path: promote G-DI2 to required for M1 when DatePicker is used. |
| RA-2 | High | DatePicker | G-DP5 (no `role="grid"` on calendar grid) means the calendar renders as an undifferentiated sequence of buttons with no structural context. When G-DP1 is fixed and keyboard navigation is added, the ARIA grid pattern (with `role="gridcell"`, `aria-label` containing full date, `aria-selected`) must be in place simultaneously — implementing arrow-key navigation without the grid role is non-conformant. The contracts specify G-DP1 and G-DP5 as independent gaps to fix separately, but they are technically co-dependent. | Mark G-DP1 and G-DP5 as "must ship together" in DatePicker.Accessibility. Without grid semantics, even a complete keyboard implementation would fail AT testing (AT interprets arrow keys inside a plain div of buttons unpredictably). |
| RA-3 | High | MultiSelect | G-MS2 (no ArrowDown/Up keyboard navigation) is marked "Accepted-risk M1" with no alternative. The trigger has `role="combobox"` and `aria-expanded`, which tells AT this is a combobox — but a combobox with no arrow-key navigation is a WCAG 2.1.1 (Keyboard) failure. A keyboard user who opens the listbox via click cannot then select any option from the keyboard. The contract does not offer a typed search workaround, and the search input (which does get focus) is not wired to any keyboard-commit mechanism. | Either (a) remove `role="combobox"` and replace with a simpler announced pattern that sets correct expectations, or (b) mark G-MS2 as M1 blocking and require arrow-key navigation before shipping. The current state — claiming combobox role without combobox keyboard behaviour — is a hard ARIA 1.2 pattern failure. |
| RA-4 | High | Upload | G-UPL7 (no `aria-live` region for upload status changes) + G-UPL6 (progress bar missing `role="progressbar"` / `aria-valuenow`) are both "Accepted-risk M1." A screen-reader user who triggers an upload gets zero feedback — no status change announcement, no progress, no success/error announcement. For an async operation whose only UI feedback is progress and status changes, silent failure for AT users is a WCAG 4.1.3 (Status Messages) violation. | Add `role="progressbar"` with `aria-valuenow`, `aria-valuemin`, `aria-valuemax` to the progress element (G-UPL6). Add a `role="status"` or `role="log"` live region that receives status transition text (uploading / success / error) (G-UPL7). Both are low implementation cost; the "Accepted-risk M1" disposition is disproportionate to the effort. |
| RA-5 | High | Tooltip | G-TT4 (no `aria-describedby` linking trigger to the tooltip element) means that even though the component correctly renders `role="tooltip"`, AT will never announce the tooltip content when the trigger is focused. The WAI-ARIA tooltip pattern requires the trigger to carry `aria-describedby={tooltipId}`. G-TT5 (conditionally rendered tooltip has unstable id) is the root blocker for fixing G-TT4 — but both are marked "Accepted-risk M1." A tooltip that AT never announces is not a tooltip — it is hover-only decoration. Any production use of Tooltip for conveying supplementary information (which is its stated purpose) silently excludes keyboard and AT users. | Always render the tooltip `<span>` in the DOM with `hidden` or `visibility: hidden` rather than conditional mount, assign a stable `id`, and set `aria-describedby` on the trigger. This resolves both G-TT4 and G-TT5 and matches the standard WAI-ARIA tooltip authoring pattern. The current conditionally-rendered approach requires a full contract revision before shipping. |
| RA-6 | High | Switch | G-SW3 (no `aria-invalid` on Switch) means an error state on a Switch cannot be communicated to AT. For boolean-type fields where a specific state is required (e.g., "You must accept terms"), validation failure is completely silent for AT users. The contract's dual-element approach (hidden `<input type="checkbox">` + visual `<span role="switch">`) also creates a G-SW1 risk: some AT may announce the control twice ("checkbox unchecked, switch off"). | Set `aria-invalid` on the hidden `<input>` (the AT-reachable element) to mirror the Switch's error state. For G-SW1 (double announcement), add `aria-hidden="true"` to the `<span role="switch">` so AT uses only the native checkbox for announcements, OR use a single element: a native `<button role="switch">` which avoids the dual-element problem entirely. |
| RA-7 | Medium | TextField | No `readOnly` state is specified in Semantic, Interaction, or Accessibility contracts. There is no `readOnly` prop and no spec for how the component would behave or announce itself if an implementer adds one. Production forms frequently need read-only display of data within a form context (e.g., a computed value shown inline with editable fields). Without spec, implementers will add `readOnly` ad hoc — possibly omitting `aria-readonly="true"` or forgetting that read-only inputs remain focusable and tabbable (unlike `disabled`). | Add `readOnly?: boolean` to the Semantic contract with explicit spec: maps to the native `readonly` attribute, emits `aria-readonly="true"` (WAI-ARIA), remains in tab order, accepts no keyboard input. Document the contrast requirement (read-only is NOT exempt from contrast minimums, unlike disabled). |
| RA-8 | Medium | TextField, SelectField, MultiSelect | All three components have a `loading` or `async` usage pattern that the contracts do not address. TextField has no `loading` state. SelectField's `options` is synchronous-only with "pre-load eagerly" as the stated workaround. MultiSelect has no `loading` state. Production forms that populate options asynchronously (e.g., a vendor dropdown loaded from an API) have no spec for how to indicate loading state to sighted users or AT. The gap is unregistered — it appears in none of the known-gaps tables. | Add a `loading?: boolean` prop (or equivalent pattern) to SelectField and MultiSelect Semantic contracts, specifying: visual spinner treatment (Styling), `aria-busy="true"` on the trigger while loading (Accessibility), and `aria-label` update or live-region announcement when options become available. |
| RA-9 | Medium | DateInput, DatePicker | G-DI2 (no `aria-invalid` on DateInput) is cascaded silently into DatePicker because DatePicker extends DateInput. The DatePicker contract acknowledges inheriting DateInput behaviour but does NOT call out this inherited gap by name. An implementer building DatePicker's error state will naturally look at DatePicker.Accessibility — which mentions nothing about `aria-invalid` — and will not discover the gap unless they also read DateInput.Accessibility. | DatePicker.Accessibility should explicitly re-list inherited gaps that affect its own accessibility surface. Specifically, add: "Inherited gap G-DI2: DatePicker does not emit `aria-invalid` on the DateInput in error mode — the error state is visually indicated but not programmatically determinable." |
| RA-10 | Medium | Dialog | Gap G4 (initial focus on close button rather than first form field) is documented as "acceptable but not ideal." For a Dialog containing a form (the primary production use case per §7's own text), landing initial focus on the close `×` button means the first Tab action moves to the first form field — but AT users hear "Close, button" as the very first announcement on dialog open. This can cause confusion about the dialog's purpose. The spec does not mandate a test requirement that verifies initial focus is appropriate for the dialog's content type. | Add a gate to the Definition of Done: "If `children` contains a form, verify via E2E test that initial focus is on the first form field (not the close button). Add `onOpenAutoFocus` usage guidance to Interaction §2." The current G4 note is a design smell acknowledged without an enforcement path. |
| RA-11 | Medium | Upload | G-UPL4 (maxFileSize silently excludes oversized files with no user notification) is marked "Low" severity, but silent exclusion is a WCAG 3.3.1 (Error Identification) and 4.1.3 (Status Messages) risk. A user selects 10 files; 3 exceed the size limit; the UI shows 7 files in the list with no indication that 3 were dropped. The contract rates this Low because "it only affects oversized files," but the user has no knowledge that their selection was partially rejected. | Raise G-UPL4 severity to Medium. Add a spec requirement: when `maxFileSize` filtering removes files, at minimum emit an `onRejected` callback with the rejected file list and its reason; the default implementation should render a visible + AT-announced error per rejected file. |
| RA-12 | Medium | FormField | FormField.Accessibility §4.1 documents that when both `hint` and `error` are supplied, the hint `<p>` is not rendered and `describedBy` resolves to error-id only. This means that a hint providing essential input-format instructions (e.g., "Format: YYYY-MM-DD") disappears when the user makes a mistake. AT users receive only "invalid entry" from `aria-invalid` and the error message — the format hint they need to correct their entry is gone. This is the worst moment to remove the hint. | Change the M1 contract to render both hint and error simultaneously (hint stays visible in a lower-opacity style; both ids in `describedBy`). The current "error-replaces-hint" behavior is a usability trap for AT users who need both signals simultaneously. If council prefers the current behavior, at minimum require that format hints be included in the error message text rather than a separate hint. |
| RA-13 | Medium | SelectField | The Accessibility contract (§12) documents that when `options.length === 0`, AT users "hear an empty listbox" with no message. The contract notes this as Gap G2 and recommends a follow-on `emptyMessage` prop. However, the Interaction contract does NOT document what should happen — there is no behavioral spec for the empty-options case (no keyboard behavior, no close-on-open). An implementer reading only Interaction.md will not know an empty listbox is a concern. The Styling contract also mentions this as an open question without a gap ID. | Add G2 (empty popover) to SelectField.Interaction's known gaps table and to SelectField.Styling's known gaps. The gap exists across all four contracts but is only acknowledged in one — implementation from the Interaction contract alone would miss it. |
| RA-14 | Medium | MultiSelect | G-MS3 (form submission omission) is marked "Medium, Accepted-risk M1." The `name` prop is described as being applied to the search `<input>`, not to a hidden multi-value input for form submission. This means a MultiSelect inside a `<form>` with native submission submits a text string (the current search text, if any) rather than the selected values. Any host using MultiSelect in a conventional form POST will submit wrong data silently. The contract does not indicate that MultiSelect is unsupported in native-form contexts, leaving the door open for a production bug. | Explicitly document in MultiSelect.Semantic §6 (FormField integration) that MultiSelect DOES NOT participate in native form submission in M1. Hosts using standard form POST must extract values from the `value[]` prop manually. This is a non-obvious constraint that deserves a prominent warning, not just a gap table entry. |
| RA-15 | Low | Dialog | Gap G2 (missing `motion-reduce:animate-none` variant) is correctly identified but the severity is understated in the text. The contract calls the violation "subjective" because the animation is "short — 150ms." However, for users with vestibular disorders who have explicitly requested `prefers-reduced-motion`, even a 150ms zoom + slide is contraindicated. The WCAG SC 2.3.3 criterion does not have a duration exemption. The "subjective" framing in the contract is inaccurate and risks the team deprioritizing the fix. | Remove the "subjective" qualifier from the G2 description. The fix (adding `motion-reduce:animate-none` to two CSS rules) is trivial. Mark as required before the next release candidate, not as a follow-on. |
| RA-16 | Low | Upload | G-UPL8 (`aria-label="Remove"` does not include the filename) is marked "Low." In practice, a user with multiple uploading files who needs to cancel a specific one cannot determine which remove button removes which file — all remove buttons have the identical accessible name "Remove." This is a WCAG 2.5.3 (Label in Name) edge case that will affect AT users in typical multi-file upload workflows. | Change the remove button accessible name to `aria-label="Remove {file.name}"`. This is a one-line fix in the implementation and should be a required correction, not a "Low / Accepted-risk" deferral. |
| RA-17 | Low | DatePicker | DatePicker.Styling §2 specifies the calendar-button content as a 📅 emoji. DatePicker.Accessibility §2 lists G-DP8 noting the emoji "is not `aria-hidden` — some AT may announce it." The calendar button has `aria-label="Open calendar"` which is correct — but if the emoji is not `aria-hidden`, AT may announce "Open calendar, 📅, button" (with the emoji character name pronounced). The fix is trivial (`aria-hidden="true"` on the emoji), but the gap is accepted as-is. | Mark G-DP8 as a required fix: add `aria-hidden="true"` to the emoji span. This is a one-character DOM change and should not be accepted as a production risk. |
| RA-18 | Low | TextField | Interaction §3 specifies the visible focus ring as `focus:outline-none focus:ring-1` and notes "In `error` mode the focus ring colour shifts to red; in the normal mode it's blue." Accessibility §8 confirms: "The recipe `focus:outline-none focus:ring-1` suppresses the browser's default outline and replaces it with a token-driven ring." The Styling contract confirms the concrete values (`focus:ring-blue-500` / `focus:ring-red-500`). However, no contract specifies the focus ring's MINIMUM WIDTH — `ring-1` is 1px. WCAG 2.4.11 (Focus Not Obscured) and 2.4.13 (Focus Appearance) both have considerations about focus indicator area. A 1px ring of 3:1 contrast against the host surface is technically WCAG 2.4.7 compliant but fails the stricter WCAG 2.4.13 AA criterion (which requires the focus indicator area to be at least the perimeter × 2px). | Add a note to TextField.Styling §3.1 and TextField.Accessibility §8: "The 1px ring (`ring-1`) is WCAG 2.4.7 (Focus Visible) compliant but does not meet the stricter WCAG 2.4.13 (Focus Appearance) criterion which requires a ≥2px thick indicator. If WCAG 2.4.13 compliance is required, upgrade to `ring-2`." This is a forward-compat note that prevents silent non-conformance when the project targets 2.4.13. |

## Cross-cutting Risk Summary

| Risk Theme | Affected Components | Production Impact |
|---|---|---|
| Keyboard-only path broken (AT cannot operate without mouse) | DatePicker (G-DP1), MultiSelect (G-MS2) | Keyboard users cannot set dates or multi-select values |
| No AT feedback for async operations | Upload (G-UPL6/7) | Upload success/failure invisible to screen readers |
| Tooltip never announces to AT | Tooltip (G-TT4/5) | Any Tooltip used for informational content is hover-only |
| Error state not communicated to AT | DateInput (G-DI2), Switch (G-SW3) | AT users cannot detect invalid fields |
| Silent data loss | Upload maxFileSize (G-UPL4), MultiSelect form submission (G-MS3) | Files silently dropped; form submits wrong values |
| ARIA role without matching keyboard pattern | MultiSelect (G-MS2 + `role="combobox"`) | Hard ARIA 1.2 non-conformance that AT testing will fail |
