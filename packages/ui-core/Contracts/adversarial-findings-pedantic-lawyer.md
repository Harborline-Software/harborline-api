# Adversarial Review — Pedantic Lawyer Perspective
Date: 2026-06-05

## Summary

Across 652 contract files, the primary systemic problems are Gap ID prefix collisions (the same 2-3-letter prefix is independently assigned to multiple unrelated components), a callback naming split between `onChange` and `onValueChange` that is unresolved across sibling components, and three incompatible header/metadata formats coexisting in the same directory. Individual findings below, ordered high-to-low by severity.

---

## Findings

| Finding ID | Severity | Component(s) | Description | Suggested Fix |
|---|---|---|---|---|
| PL-1 | High | CopyButton, CodeBlock, CheckBox/CheckboxField | **Gap ID prefix collision: `G-CB`** is independently claimed by three separate components. `CopyButton` defines `G-CB1` (clipboard error) and `G-CB2` (rapid reclicks). `CodeBlock` defines `G-CB1` (copy-button positioning), `G-CB2` (line-number AT exposure), `G-CB3` (missing aria-label). `CheckBox` defines `G-CB4`–`G-CB7`. `CheckboxField.Semantic.md` claims to "close" `G-CB1` and `G-CB2` (intended as CheckBox gaps). Any tool or cross-reference that searches for `G-CB1` will match three distinct bugs in three distinct components. | Rename: CopyButton → `G-CPBTN1/2`; CodeBlock → `G-CBLK1/2/3`; CheckBox → `G-CHK1`–`G-CHK7`; update CheckboxField closes-references to match. |
| PL-2 | High | TileLayout, Timeline, TreeList | **Gap ID prefix collision: `G-TL`** is claimed by three unrelated components in two categories. `TileLayout` (Layout) defines `G-TL1`–`G-TL6`. `Timeline` (DataDisplay) defines `G-TL1`, `G-TL2`. `TreeList` (DataDisplay) defines `G-TL1`, `G-TL2`. All three define `G-TL1` and `G-TL2` as different bugs. | Rename: TileLayout → `G-TLAYOUT1`–`G-TLAYOUT6`; Timeline → `G-TMLN1`, `G-TMLN2`; TreeList → `G-TRLST1`, `G-TRLST2`. |
| PL-3 | High | TaskBoard, Toolbar | **Gap ID prefix collision: `G-TB`** is shared between TaskBoard (Scheduling) and Toolbar (Navigation). `G-TB1` = drag-and-drop keyboard gap (TaskBoard) and `G-TB1` = missing `role="toolbar"` (Toolbar). `G-TB2` = column reorder out-of-scope (TaskBoard) and `G-TB2` = no roving-tabIndex (Toolbar). | Rename: TaskBoard → `G-TSKBD1/2`; Toolbar → `G-TLBR1/2`. |
| PL-4 | High | Splitter, Spinner | **Gap ID prefix collision: `G-SP`** is shared between Splitter (Layout) and Spinner (Feedback). `G-SP1` = no keyboard resize (Splitter) and `G-SP1` = `role="status"` on SVG may not create live region (Spinner). Splitter defines `G-SP1`–`G-SP6`; Spinner defines `G-SP1` only. | Rename: Spinner → `G-SPNR1`; Splitter keeps `G-SP1`–`G-SP6`, or rename Splitter to `G-SPLT1`–`G-SPLT6`. |
| PL-5 | High | Popup, Popover | **Gap ID prefix collision: `G-POP`** is shared between Popup and Popover (both in Overlays). `G-POP1` = popup position drift on scroll (Popup.Interaction) and `G-POP1` = no default `aria-label` on PopoverContent (Popover.Accessibility). These are different bugs in different components with the same ID. | Rename: Popup → `G-PPUP1`; Popover → `G-PPOVR1`. |
| PL-6 | High | Accordion, AutoComplete | **Gap ID prefix collision: `G-AC`** is shared between Accordion (Layout) and AutoComplete (DataEntry). `G-AC1` = hardcoded `<h3>` heading level (Accordion.Accessibility) and `G-AC2`–`G-AC6` are AutoComplete ARIA gaps. The gap numbering range overlaps making it appear Accordion and AutoComplete are part of the same component family. | Rename: Accordion → `G-ACCORD1`; AutoComplete keeps `G-AC2`–`G-AC6` (if clarified that AC=AutoComplete only). |
| PL-7 | High | AIPrompt, Chat | **Suggestion chip display-text field name diverges between sibling AI components.** `AIPromptSuggestion` uses `title: string` and optional `subtitle?: string` for display text. `ChatSuggestion` uses `label: string` (no subtitle). These are semantically the same "text shown on the chip" concept across components in the same AI family, authored by the same spec. | Standardize on one field name across the AI component family. Options: (a) use `label` everywhere (simpler, no subtitle); (b) use `title`/`subtitle` everywhere (Chat gains optional subtitle). Either way, pick one and apply it to both. |
| PL-8 | High | AIPrompt, Chat, InlineAIPrompt | **Submit callback name diverges between sibling AI components.** `AIPrompt` uses `onPromptRequest: (prompt: string) => void`. `Chat` uses `onSend: (content: string) => void`. `InlineAIPrompt` uses `onPromptRequest`. The payload parameter name also differs (`prompt` vs `content`). All three props mean "the user submitted text to the AI." | Standardize on one name. Recommendation: `onSubmit: (prompt: string) => void` across all three AI components (avoids clashing with Form's `onSubmit` by payload type, but more intuitive than `onPromptRequest`). Alternatively, keep `onPromptRequest` and apply it to Chat as well. |
| PL-9 | Medium | Calendar (Scheduling), DateInput (DataEntry) | **`onChange` vs `onValueChange` split between Calendar and DateInput for the same "date changed" event.** `Calendar.Semantic.md` declares `onChange?: (date: Date | null) => void`. `DateInput.Semantic.md` declares `onValueChange?: (date: Date | null) => void`. `DatePicker` extends `DateInputProps` (inheriting `onValueChange`) and internally calls `onValueChange`. A consumer who uses both `Calendar` and `DatePicker` in the same form must wire two different callback names for the same concept. | Align to `onValueChange` fleet-wide for value-bearing controls (the majority pattern across DataEntry). Update `Calendar.Semantic.md` §2. |
| PL-10 | Medium | Switch, CheckBox | **Boolean control callback name split.** `Switch` declares `onCheckedChange?: (checked: boolean) => void`. `CheckBox` declares `onChange?: (checked: boolean \| 'indeterminate') => void`. Both are boolean on/off controls. The naming is inconsistent; consumers composing a form with both controls face two different callback names for the same category of event. | Standardize: either both use `onChange` (simpler, consistent with HTML) or both use `onCheckedChange` (explicit). Note: `onCheckedChange` is the Radix UI convention for `Checkbox`; if Radix is the foundation, align both to it. |
| PL-11 | Medium | RadialGauge | **`RadialGaugeProps` interface is not formally defined in the contract.** `RadialGauge.Semantic.md §2` says "Same interface as `CircularGaugeProps`. See `CircularGauge.Semantic.md`." There is no TypeScript interface definition in the RadialGauge contract. Every other parent/alias pair (DonutChart, ColumnChart, MultiViewCalendar) either extends or explicitly declares its interface. A developer reading only `RadialGauge.Semantic.md` must go read a second file to understand the API. | Either embed `interface RadialGaugeProps extends CircularGaugeProps {}` plus a note about the additional tick-mark behavior, or explicitly re-state the relevant props. The `extends` form makes the relationship machine-verifiable. |
| PL-12 | Medium | DataGrid | **Gap IDs use two non-standard formats.** `DataGrid.Accessibility.md §15` uses bare sequential IDs: `G1`, `G2`, `G3`, … `G10` (no component prefix, no hyphen). `DataGrid.Semantic.md` uses `G-C1`, `G-C3`, `G-C5` (C probably means "Contract", not "Component"; `G-C2` and `G-C4` are never defined — gaps in the sequence). Every other component uses `G-COMPABBR-N` or `G-COMPABRN` format. These bare IDs are ungrepable: a search for `G-C1` will match DataGrid items and potentially conflict with any future component using a `C` prefix. | Rename DataGrid gaps to `G-DG1`–`G-DG10` (Accessibility) and `G-DG-S1`, `G-DG-S3`, `G-DG-S5` (Semantic, to distinguish the section-level gaps); update all cross-references within the four DataGrid contracts. |
| PL-13 | Medium | StatusBanner (3 of 4 contracts) | **Three of the four StatusBanner contracts (`Semantic`, `Styling`, `Accessibility`) use a non-standard flat-text header format** (`ADR: 0017-A1` / `Family: Feedback` / `Status: Accepted`) instead of the universal markdown bullet-list format (`- **Status:** Accepted`, `- **Phase:** …`, etc.) used by all other 648+ contracts. `StatusBanner.Interaction.md` correctly uses the standard format. The three flat-header files also lack a `Phase:` line entirely (the only contracts in the corpus missing Phase). | Reformat the three non-standard headers to match the standard bullet-list format. Add `- **Phase:** ADR 0017-A1 Phase M1` to each. |
| PL-14 | Medium | SwitchField, ComboBoxField, Accordion, Stepper | **Phase annotation inconsistency within the same component's four-contract family.** For these four components, the `Semantic.md` file says `Phase M1 (R8 priority bump)` or `Phase M1 (R9 new component)` while the sibling `Interaction.md`, `Accessibility.md`, and `Styling.md` say the plain `Phase M1` with no annotation. A reader checking only the Accessibility contract would not know this component was a priority-bumped R8 item. | Either propagate the `(R8/R9)` annotation to all four sibling contracts for affected components, or remove it from the Semantic and rely on the spec-audit / backlog files to carry the priority history. |
| PL-15 | Medium | ColumnChart (DataVisualization) | **Reference implementation note incorrectly states Recharts layout direction.** `ColumnChart.Semantic.md` header says: "source: Recharts BarChart **layout=vertical** / Telerik Column Chart baseline." In Recharts, `layout="vertical"` means categories are on the Y-axis and bars run horizontally (i.e., a horizontal bar chart — what the spec calls `BarChart`). For a vertical column chart, Recharts uses `layout="horizontal"`. The spec's own internal `layout` prop definition is internally consistent but the reference note is inverted relative to the Recharts API it cites. Any implementer who reads the reference note and looks up the Recharts docs will get the wrong layout value. | Fix the reference note to read "Recharts BarChart **layout=horizontal**" for ColumnChart. Optionally add a cross-note in `BarChart.Semantic.md` stating that the spec's `layout` prop orientation is the inverse of Recharts naming to prevent future confusion. |
| PL-16 | Medium | PanelBar (Layout) | **Broken relative path in Canonical contracts link.** `PanelBar.Semantic.md` declares `- **Canonical contracts:** [Accordion](../Feedback/Accordion.Semantic.md)` but Accordion lives in the `Layout/` directory, not `Feedback/`. The path `../Feedback/Accordion.Semantic.md` resolves to a non-existent file. PanelBar's `- **Reference implementation:**` also says `packages/ui-react/src/components/feedback/Accordion.tsx` while `Accordion.Semantic.md` itself says the implementation is at `packages/ui-react/src/components/layout/Accordion.tsx`. | Fix PanelBar.Semantic.md canonical link to `./Accordion.Semantic.md` and reference implementation path to `packages/ui-react/src/components/layout/Accordion.tsx`. |
| PL-17 | Medium | DataGrid | **Non-sequential gap IDs in Semantic contract.** `DataGrid.Semantic.md` uses `G-C1`, `G-C3`, `G-C5` — skipping `G-C2` and `G-C4`. Neither `G-C2` nor `G-C4` is defined anywhere in the corpus. Gap IDs that skip numbers imply gaps were deleted but the remaining IDs were not renumbered, making the sequence hard to reason about. | Define and document `G-C2` and `G-C4` (if they represent real gaps that were tracked elsewhere), or renumber to `G-C1`, `G-C2`, `G-C3` to close the sequence holes. |
| PL-18 | Low | All 16 Semantic-only alias contracts (ButtonGroup, ToggleButton, SegmentedControl, RichTextEditor, PanelBar, ScrollView, ChunkProgressBar, etc.) | **Components with a single `Semantic.md` (alias redirect) have no companion `Interaction`, `Accessibility`, or `Styling` contracts.** The header lists them as having full 4-contract coverage implicitly. The "`find`-for-missing-contracts" check shows 16 components with zero companion contracts. For alias components this is by design — but the contract header does not say "Contract type: Semantic (alias redirect — all behavior in canonical component)" clearly enough to distinguish from a genuine incomplete contract set. Automation that checks for complete 4-contract coverage will report 16 false positives. | Add a dedicated `- **Coverage note:** Alias redirect — no separate Interaction/Accessibility/Styling contracts. Canonical coverage in [X](./X.Semantic.md).` line to each alias contract header, making the omission explicit. |
| PL-19 | Low | Phase M2 declarations across multiple categories | **Phase M2 is declared in three different verbosity levels within a single corpus.** Files use: (1) `Phase M2`, (2) `Phase M2 (forward-spec)`, (3) `Phase M2 (forward-spec; component not yet implemented)`. All three mean the same thing. The minimal form `Phase M2` provides no information beyond the phase number, while the full form is clearest. | Standardize to `Phase M2 (forward-spec; component not yet implemented)` as the canonical form. |
| PL-20 | Low | LinearGauge | **Vague gap cross-reference.** `LinearGauge.Accessibility.md §3` says "Same as CircularGauge (G-CGAUGE-A1 **equivalent** for range band colors)." The word "equivalent" is ambiguous — it could mean "the same gap ID applies" or "a similar but distinct gap exists." Compare with `RadialGauge.Accessibility.md §2` which says "Same as CircularGauge (G-CGAUGE-A1)" without the qualifier. Both should state whether the gap ID is literally shared or whether LinearGauge should carry its own gap ID (e.g., `G-LGAUGE-A1`). | Remove "equivalent" wording. Either state the shared gap explicitly: "Inherits G-CGAUGE-A1; see `CircularGauge.Accessibility.md`" or assign LinearGauge its own gap ID. |
| PL-21 | Low | InlineAIPrompt | **`AIPromptOutput` referenced but not imported or embedded.** `InlineAIPrompt.Semantic.md §2` declares `output?: AIPromptOutput | null` in the interface without defining `AIPromptOutput`, and §3 says "`AIPromptOutput` is identical to AIPrompt Semantic §2." A reader has a dangling type reference. DonutChart and MultiViewCalendar handle this correctly by using `extends` or reproducing the type. | Either embed the `AIPromptOutput` interface definition in `InlineAIPrompt.Semantic.md` or add a formal `import`-style note: "`AIPromptOutput` — see `AIPrompt.Semantic.md §2`." |
| PL-22 | Low | ColumnChart | **`layout?: 'vertical'` is declared as optional but described as "forced" and "not configurable."** If the prop is forced to `'vertical'`, it should not appear in the `interface ColumnChartProps` at all (since it is omitted via `Omit<BarChartProps, 'layout'>` and only the single valid value is re-added). Declaring it optional (`?:`) means callers could omit it (fine) but also makes it look configurable. The comment "forced to 'vertical' in ColumnChart; not configurable" contradicts `?:` syntax. | Remove the `layout?: 'vertical'` prop from the interface entirely (since `Omit<BarChartProps, 'layout'>` already excises it) and add a prose note: "ColumnChart does not expose a `layout` prop. The orientation is fixed to vertical." |

## Scope note

All 652 contract files were surveyed for header consistency and pattern conformance. Alias-redirect contracts, partially-contracted components (Utility / DataQuery / KeyboardNavigation / etc.), and both StatusBanner format anomalies were verified by file read. Gap ID collision analysis was performed via corpus-wide grep. The Recharts layout inversion (PL-15) and RadialGaugeProps omission (PL-11) were verified by direct file read. No spec files were modified.
