# T-974 asset-registry entity create ID refusal, pending mutation verification

The public seam is `POST /api/local-node/asset-registry/entities` through the production `AssetRegistryRoutes.Map` handler and an in-process HTTP listener. The risk is accepting a client-constructed new record `id` and silently replacing it with a server ID. `AssetRegistryRouteTests.Entities_Create_RefusesClientSuppliedRecordId` was written first and failed with expected 400 versus actual 201 Created. After the request body captured `id` and the route refused it, the focused test passed 1/1; it also observes through the public list route that no entity was persisted. The existing `Entities_Create_Get_List` test is the positive server-minted control. The first route-class run passed 35/35.

Review then identified a permission-order boundary: a denied caller with a supplied `id` must receive the write-gate refusal before validation. `Entities_Create_DenialPrecedesClientSuppliedRecordIdRefusal` failed red with expected 403 versus actual 400. The route now invokes the existing `RequestAuthorization` gate only on the invalid-ID path before returning 400; valid create requests retain their existing write path. The focused test passed 1/1, the route class passed 36/36, and no refactor was needed. The first affected-project rerun exposed a false positive in `AssetRegistryAuthorizedReadFenceTests`: it counted the newly gated create handler as an entity read because its inventory included every repository method. Restricting that existing inventory to `GetByIdAsync`, `ListByTenantAsync` and `ListByTypeAsync` made its focused test pass 1/1.
