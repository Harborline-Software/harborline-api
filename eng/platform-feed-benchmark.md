# Disposable full-build measurement

Dispatch the existing `platform-feed-qualification.yml` workflow on the reviewed benchmark branch with `benchmark=true`. It runs three independent hosted Linux pairs. Each pair executes cold, warm and forced-miss cases at the same clean candidate commit, Node binary, host SDK and immutable Linux SDK image. The benchmark is a JavaScript action so the runner supplies its service-scoped runtime token; build children receive credential-stripped environments.

Only `api356-benchmark-<run>-<attempt>-<pair>-<input-fingerprint>-{bundle,forcedmiss}` keys are accessed. The version is dedicated to raw test bundles. A cold case independently restores the pinned platform, captures the complete producing/restored input closure, packs fresh packages and publishes its bundle. The controller retains that bundle digest before candidate tests execute. Warm reads use the exact key and validate downloaded bytes against that independent digest, current input closure and complete package inventory. Misses, malformed transport replies and unusable bundles take the full fresh pack route; they cannot qualify the warm-hit control. Nothing promotes these benchmark entries into a production cache, package release or validation verdict.

Every case runs the real host preflight and full destination exact-clone gate, including fresh .NET restore/build, consumption diagnostics, host tests, capability tests, architecture/boundary checks and both baseline comparisons. Candidate test identities and counts must agree across the three cases; passing recorded evidence must name the dispatched candidate. These byte checks are consistency diagnostics, not a claim of tamper resistance against arbitrary candidate execution. Production producer authentication and the separate synthetic service-isolation/denial qualification remain distinct acceptance requirements.

Measurements include clone, independent platform restore and input verification, cache transfer, bundle checks, fresh pack fallback, handoff, and full host work. The immutable image is pulled during common setup so only cold does not pay that setup cost. Common checkout/tool setup/image time is recorded and added equally to the per-case totals for a second comparison. NuGet, npm and pnpm package stores are fresh per case, and compiler/MSBuild server reuse is disabled for API builds. Cases still run in fixed cold/warm/miss order; OS page cache, network variation and hosted-runner scheduling can affect results. Three pairs are a bounded measurement, not causal attribution of every timing difference.

Cold totals include experimental cache publication. Report that cost separately: the net consumer comparison subtracts publication from cold, retains download and verification in warm, and reports negative or negligible benefit honestly. Preserve the full totals and the comparison including common setup alongside that figure. Evidence artifact upload and runner queue delays are outside the per-case clock; use job metadata if reporting complete workflow latency. No performance claim is valid unless all three hosted pairs complete with real warm hits, forced misses, equal work and fresh passing gates. Reuse authorization stays false.

Failed cases preserve the phase and timings already incurred before cleanup, without entering the successful-results comparison. Current-commit exact-clone diagnostics retain only stage identifiers, verdicts, durations, exit codes, test counts and bounded failure identities; the last structured progress stage is retained when a complete report is unavailable. Raw logs, paths, URLs and exception messages are excluded. A tracked historical exact-clone report is rejected by commit identity. Successful cases also report observed inventory counts and identity digests so equal validation work is reviewable.

Failure identity records always retain a SHA-256 digest. Plain custom xUnit titles and relative Vitest identities may also carry a bounded display; unsafe or long identities remain digest-only. Total failure counts remain visible when the 64-identity cap is reached. Failed boundary logs yield only bounded failing Node test titles, a captured-tail digest and fixed diagnostic codes before scratch cleanup. The disk read is limited to the final 256 KiB and explicitly marks partial evidence. The benchmark test suite is registered in the required boundary runner, so its transport, fallback, provenance and workflow checks run in normal gates.
