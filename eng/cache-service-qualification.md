# Synthetic cache service qualification

This manual qualification tests GitHub's cache-service write authority and branch namespace isolation. It does not enable package reuse, skip validation, or claim that arbitrary PR execution is tamper-resistant. It uses only literal fixtures under `api356-synthetic-<seed-run-id>-<random-nonce>` and a dedicated version hash. Nothing reads, writes or deletes existing package/release cache entries.

The main-only `seed` and `read` jobs check out their reviewed workflow SHA. Their code does not execute candidate code or use candidate-selected publishers. The two PR jobs are deliberately lower trust: one explicitly requests `cache-mode: write` and calls the cache v2 API directly, including a `metadata.scope` main-ref override. The other changes its local `ACTIONS_CACHE_MODE` variable before a direct reservation attempt with a service read-only token. No elevated GitHub token, secret or repository setting is required.

Run `cache-service-qualification.yml` on main with `mode=seed`. Record the namespace from its bounded artifact. Add the exact line `Cache qualification namespace: <namespace>` to the test PR body after the PR contains this qualification workflow and action. That runs the candidate and read-only controls on a real `refs/pull/<number>/merge` service context. After both complete, dispatch the main workflow with `mode=read` and that namespace. Each experiment uses a fresh seed; do not rerun writes against a completed namespace.

The candidate must first read the original literal fixture, then successfully write and read its altered fixture and PR-only key. An accepted scope-override request is inconclusive until the fresh main reader runs. The main reader must see the original literal fixture and no PR-only or override entry. A read-only reservation must receive HTTP 403 after the client variable changes. Unavailable services, malformed responses, missing positive controls, or any failed job provide no passing security verdict. Evidence contains only fixed operation names, keys' suffixes, status codes and non-secret workflow identity; runtime tokens and signed blob URLs are never logged.

The harness speaks the official cache v2 Twirp request schema directly, bypassing a restore-only action's client checks. Its fixtures are small raw byte objects, deliberately outside the package-cache format. The protocol is grounded in `actions/toolkit`'s `packages/cache/src/generated/results/api/v1/cache.ts` and `entities/v1/cachemetadata.ts`. GitHub documents service-scoped cache tokens and merge-ref isolation in its [dependency caching reference](https://docs.github.com/en/actions/reference/workflows-and-actions/dependency-caching). Live results, rather than client environment variables, determine whether this repository/service supports those guarantees.

After isolation qualification, a separate package experiment must cover producing source, builder closure, immutable SDK profile, architecture, NuGet configuration and dependency pins in its exact compatibility key. A miss or unusable entry requires the full fresh build. PR outputs must never be promoted into main caches or release inputs. Measure at least three paired cold, warm and forced-miss full builds, including download, extraction, restore, compilation and tests, before claiming any benefit. Cache authority, fresh candidate build execution and validation verdict reuse are separate claims; verdict reuse remains disabled.
