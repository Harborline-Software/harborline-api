# Adversarial Review — Pedantic Lawyer

**Date:** 2026-06-06
**Spec set:** `packages/ui-core/Contracts/` (972 contract files across 78+ components)
**Perspective:** Pedantic Lawyer — are terms used consistently?

---

## Summary

Six categories of terminology inconsistency were identified across the corpus. The two highest-severity findings (PL-1 and PL-2) are API-surface inconsistencies that will produce real implementor confusion: boolean-toggle controls split across two distinct change-callback names (`onChange` vs `onCheckedChange`) with no documented rationale, and required-prop notation splits between `_required_` (italic markdown) and bare `required` across 17 vs 45 occurrences respectively. The remaining four findings are structural inconsistencies — gap section heading variants, gap table column-ordering inconsistency across ~39 files, the three-way Known Gaps heading suffix proliferation, and one non-standard file header format that survived remediation of similar issues in earlier adversarial passes.

None of the findings represent invented gaps. Every claim below is supported by grep evidence from the corpus.

## Additional note: `FieldWrapper` / `FormField` alias disambiguation

The catalog (`component-master-catalog.md` row 55) lists `FieldWrapper` as `alias: FormField`. Both have separate 4-contract spec sets. The two Semantic contracts describe **overlapping but distinct** behavior:

- `FieldWrapper.Semantic.md` — does NOT provide `FormFieldContext`; CSS-driven validity treatment only; no `name` prop; requires host to wire `id` manually.
- `FormField.Semantic.md` — provides `FormFieldContext` (threaded `describedBy`); `name` prop drives `id` and hint/error node IDs; is the "WCAG 2.2 AA compliance mechanism."

The alias claim in the catalog is therefore misleading: these are not interchangeable. `InlineEdit.Semantic.md` and `AddressForm.Semantic.md` both acknowledge a split by writing "does not use `FormField` or `FieldWrapper`" — treating them as two distinct options. This is not a terminology inconsistency per se, but the alias claim in the catalog will cause implementors to substitute one for the other incorrectly. The alias line should be changed to `note: lower-level alternative to FormField (no context)` or similar.

## Verdict

The corpus is internally consistent in its large-scale structure (972 files, all with `- **Status:** Accepted`, all using the numbered-section format, all categorized by family). The inconsistencies found are concentrated in three layers:

1. **API surface** — PL-1 (`onChange` vs `onCheckedChange`) is the only finding that will cause implementors to write divergent code. It is High because two otherwise-identical boolean-toggle controls produce different host-code patterns.
2. **Prop table notation** — PL-2 (`_required_` vs `required`) is High because the distinction matters to any toolchain parsing prop metadata from the markdown files.
3. **Section/table structure** — PL-3, PL-4, PL-5 are Medium; they degrade toolchain-parsability and cross-file readability without breaking the semantic intent of any individual contract.
4. **Header format** — PL-6 is a pre-existing Low-severity residual from prior passes.

PL-1 and PL-2 should be resolved before M2 spec-freeze. PL-3 and PL-4 are mechanical sweeps that can be batched. PL-5 is a one-file two-row fix. PL-6 is a three-file header reformat.
