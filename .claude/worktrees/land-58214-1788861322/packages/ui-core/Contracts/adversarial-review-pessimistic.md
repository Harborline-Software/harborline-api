# Adversarial Review — Pessimistic Risk Assessor

**Date:** 2026-06-06
**Spec set:** packages/ui-core/Contracts/ (78-component reverse-spec set)
**Perspective:** Pessimistic Risk Assessor — what gaps cause production bugs?
**Components sampled:** 27 (DataEntry: ComboBox, AutoComplete, MultiSelect, DatePicker, DateRangePicker, Form, RadioGroup, Slider, RangeSlider, InlineEdit, CurrencyField, NumberField, NumberStepper, PinField, CreditCardField, TagInput, Switch, Upload, MultiStepForm, Wizard, FieldArray, DropDownList; Navigation: TabStrip, CommandPalette, TreeView; Overlays: Dialog, Drawer; Feedback: Sonner, ConfirmDialog, ProgressBar; DataDisplay: DataGrid)

---

## Summary

The spec set is generally well-authored — gaps are acknowledged rather than papered over, and severity ratings are honest. However, the Pessimistic Risk Assessor perspective surfaces **11 production-impact findings** that a developer implementing from these contracts alone could ship as real bugs. The dominant risk cluster is **ARIA role mismatch with keyboard contract** (six components claim interactive ARIA roles but omit the mandatory keyboard behaviour those roles require). Secondary clusters are **unacknowledged controlled/uncontrolled ambiguity** (three components) and **silent data loss on async interactions** (two components).

Severity distribution: 3 Critical, 7 High, 9 Medium, 5 Low.

| PR-1 | Critical | `MultiSelect.Interaction.md`, `MultiSelect.Accessibility.md` | `role="combobox"` declared on the trigger div but no `ArrowDown`/`ArrowUp` keyboard navigation exists (G-MS2). A developer reading only the Interaction contract would see the ARIA table calling out `role="combobox"`, implement the component, and ship a control that AT announces as a combobox but cannot be operated by keyboard-only users. The blocking-note in the Accessibility contract is strong — but it is in a different file from the Interaction contract. | PR-2 | Critical | `CreditCardField.Accessibility.md` | Hardcoded `id` values (`cc-number`, `cc-name`, `cc-expiry`, `cc-cvc`) cause duplicate-id failures when CreditCardField is used more than once on a page (Gap A-1). No runtime warning is emitted by React for duplicate HTML ids. | PR-3 | Critical | `ConfirmDialog.Interaction.md`, `ConfirmDialog.Accessibility.md` | No focus trap (Gap G-CD1). WCAG SC 2.1.2 requires that a modal dialog (as asserted by `aria-modal="true"`) traps focus. Furthermore, Gap G-CD4: no focus-return on close — the host must manually return focus to the trigger. If a developer uses ConfirmDialog for a destructive action (Delete Record, Void Invoice) and the host does not implement focus-return, focus is lost to `<body>` after confirmation. A developer reading these contracts as "acceptable" ships a combobox where AT users can Tab into the field, trigger ArrowDown, but receive no announcement of which option is highlighted. They must guess and press Enter blind. The same gaps exist in AutoComplete (G-AC2, G-AC3). Both are marked Accepted-risk without specifying *when* they will be fixed. | AT users cannot reliably select from ComboBox or AutoComplete without knowing which option is highlighted. Both files note these gaps are "co-dependent for keyboard accessibility." A developer building a DatePicker today implements neither the calendar keyboard path (G-DP1) nor the DateInput validation feedback (G-DI2). The only keyboard-accessible path requires the user to type a date, and if they type the wrong format they get no error feedback. The Accessibility contract's "blocking" language is correct — yet the contract Status is "Accepted." A developer implementing from these contracts will ship the blocking gaps because the status field says the spec is accepted. | AT users receive no feedback during file upload (no progress, no completion, no error). | PR-8 | High | `InlineEdit.Accessibility.md` | Gap G2: focus is NOT returned to the view button after editing. The `editing = false` transition does not call `buttonRef.current?.focus()`. If InlineEdit is used in a data table (a common ERP pattern — edit a vendor name, a line-item amount), the user cannot proceed to the next row without using the mouse to re-orient. | PR-11 | Medium | `Wizard.Accessibility.md` | Gap G-WZ3: focus is not moved to step content on step navigation. ## Cross-cutting patterns (not per-component, but systematic)

| Pattern | Affected components | Risk |
|---|---|---|
| ARIA role without keyboard behaviour | ComboBox, AutoComplete, MultiSelect, CommandPalette, TreeView (lacks ArrowUp/Down), Switch (dual-element) | Six components claim interactive ARIA roles that require keyboard navigation patterns the implementations do not provide. Implementations that pass automated axe scans (role present) will fail manual AT review (keyboard model absent). |
| No `aria-activedescendant` on combobox patterns | ComboBox (G-CBX2), AutoComplete (G-AC3), MultiSelect (G-MS1) | AT cannot announce the highlighted option as the user moves through suggestions. Affects every lookup-style input in the application. |
| Accepted-risk gaps on v1-priority components | DateRangePicker (v1), ComboBox (v1), Upload (v1), DropDownList (v1) | High/Critical gaps marked Accepted-risk M1 on components with `app-priority: v1` will ship to production in v1. |
| Focus-return not implemented | InlineEdit (G2), ConfirmDialog (G-CD4), Dialog (G1 for conditional trigger) | Three separate components fail to return focus on close. Each is individually documented but the pattern recurs, suggesting the next new overlay/edit component will also miss it. |
| Controlled/uncontrolled ambiguity | NumberStepper (NaN input silently ignored), CurrencyField (blur normalizes without a success callback), InlineEdit (empty draft does not fire onConfirm and does not restore value) | The spec describes these as Accepted-risk but does not define what the host should do to detect and handle the silent states. |

## Verdict

**Overall spec quality: B (Solid).** The contracts are honest about gaps, severity ratings are generally calibrated, and the "Blocking before production use" flags in Upload and the combobox-without-keyboard-model warnings in MultiSelect show the spec authors understood the risks. The spec set earns the B rather than C because the gaps are documented rather than hidden.

**Three findings that should block v1 ship:**

1. **PR-1 (MultiSelect)** — ships `role="combobox"` with no keyboard navigation. The Accessibility contract says this is a hard WCAG 2.1.1 failure. The blocking-note is there; it needs to become a gate.

2. **PR-3 (ConfirmDialog)** — no focus trap on a `role="dialog"` `aria-modal="true"` surface. This is the most common modal accessibility failure and is the component most likely to be used for destructive confirmation (delete, void, archive). The fix (use Radix Dialog primitives instead of a manual implementation) is also the cleanup that closes G-CD3 and G-CD4.

3. **PR-2 (CreditCardField)** — hardcoded ids. Any page with two card-entry widgets (billing/shipping split, retry-flow) silently produces incorrect label associations. Combined with no `aria-invalid`, the accessibility surface of the payment flow is broken before it ships.

**Systematic remediation recommendation:** The `aria-activedescendant` gap (PR-4) affects ComboBox, AutoComplete, and MultiSelect simultaneously. One implementation task fixes the most common lookup pattern in the application. Prioritize before the first release of any property/tenant search feature.
