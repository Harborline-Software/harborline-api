# Adversarial Review Round 3 — Devil's Advocate

**Date:** 2026-06-06
**Perspective:** Devil's Advocate — structural re-examination at 1,022 files
**Scope:** Structural validity of the 4-contract model + sampled components across all 11 categories + late-add component fit + Known Gaps tracking system + forward-spec trustworthiness
**Prior rounds read:** Yes — `adversarial-hardening-log.md` (Round 1, 88 findings, batch-31), `adversarial-hardening-log-round2.md` (Round 2, 29 findings, batch-32), `upf-meta-validation.md` (UPF Stage 2 all-pass verdict)
**Corpus growth:** 256 (pre-Round-1) → 652 (Round 1 baseline) → 660 (post-batch-32) → **1,022 (today)** — +362 contract files since Round 2 baseline with no intervening adversarial pass

---

## Summary

The 4-contract model **still holds structurally** for components in its native zone (DataDisplay, DataEntry, Overlays, Feedback, Navigation, Layout) — these are precisely the surfaces it was designed for, and sampled components (DataGrid, Card, TabStrip, Alert, Dialog, Switch) show clean non-overlapping content distribution. **The model frays at the edges** for late-added components: RoleGate is structurally a security primitive whose load-bearing concerns (server-side enforcement boundary) live in Semantic §6 with no home in the contract type system; ESignatureField scatters legal/audit concerns across Semantic + Accessibility prose without a dedicated compliance contract.

More urgently, **the corpus has outgrown its tracking machinery** between Round 2 (660 files) and today (1,022 files) — no adversarial pass covered the +362 delta, the master catalog still claims 652 files (~57% understated), the M0-backlog says 660, three late-additions (PDFEditor, ESignatureField, RoleGate — 12 contract files) are absent from the catalog entirely, and the existing Map catalog row points to a phantom that doesn't match the on-disk Map. Several Round 1 fixes logged as "Fixed-in-batch-31" were **only partially applied** (DA-1 Aliases-canonical-sha downgraded to a no-SHA link with no enforcement; DA-4 "Identical to → Extends" rewrite missed 5+ contract files that still say "Identical to" while adding unique sections).

The structural verdict from Round 1 — "4-contract model is sound; no 5th contract type needed" — **needs amendment**, not reversal. The model is sound for in-DOM interactive components but inadequate as a tracking system for the corpus now around it, and inadequate for components whose primary contract surface is legal/security/compliance rather than UI behavior. ADR 0017-A1 should add a "scope boundary" clause that names what the 4-contract model does NOT cover, and the corpus needs a catalog-promotion sweep before any further authoring waves.

## Structural verdict

**The 4-contract model from ADR 0017-A1 remains sound for components in its design center — interactive in-DOM UI components.** The sample of 10 across categories (DataGrid, TextField, Switch, Dialog, Card, TabStrip, Alert, Tooltip, CircularGauge, Chat) shows clean separation: Semantic owns props + data model, Interaction owns state + events + behavior, Accessibility owns ARIA + AT + WCAG, Styling owns tokens + Tailwind + visual states. Cross-file duplication is minimal; each contract earns its keep.

**The model needs three amendments to ADR 0017-A1 at this scale:**

### Amendment A — Scope boundary clause

Name what the 4-contract model does NOT cover:
- **Security / trust-boundary primitives** (RoleGate, future Policy-Gate, role-claim guards) — the load-bearing concern is "this is NOT the security boundary; the server is." Currently lives in Semantic §6 prose; should be either a dedicated `Trust-boundary` contract type or an explicit "single-file contract" exception.
- **Legal / compliance primitives** (ESignatureField, future Consent, AuditTrail) — load-bearing concerns are jurisdiction, audit, legally-binding semantics. Currently scattered across Semantic + Accessibility prose; should be either a dedicated `Compliance` contract type or pinned to a "compliance section" in Semantic with explicit host-responsibility callouts.

Without this amendment, the 4-contract template will continue to force empty contracts for these primitives while load-bearing concerns hide in prose.

### Amendment B — Skip-contract convention

For components where one of the four contract types is genuinely N/A (RoleGate Styling, CircularGauge Interaction, ButtonGroup alias-redirects), permit a single-paragraph file with a header marker (`Skip-rationale: <reason>`) instead of a 30+ line file padded with "this is empty by design." The Round 1 DA-2 fix added a header paragraph declaring "Display-only" — formalize that pattern as the skip-contract convention.

### Amendment C — Disposition tracking discipline

The current `Accepted-risk M1` / `Fix-deferred M2` / `Fixed-in-batch-N` vocabulary has degraded:
- 240 files claim `Accepted-risk M1`, 5 files claim `Fix-deferred M2`, but the M2-deferred work lives in hardening logs not in contracts;
- "Fixed-in-batch-31" was applied partially (DA-1, DA-4) without verification;
- Round 1 deferred items have no PR tracking or due date.

Two options: (a) drop the M1/M2 suffix; let `Accepted-risk` mean "permanent acceptance" and require `Tracked: <issue#>` for backlog items; or (b) audit all 240 `Accepted-risk M1` entries and force each to flip to `Tracked` or `Accepted`. Either way the current vocabulary is noise.

### Recommendation on corpus health

Before authoring any further waves:
1. **Catalog sweep** (blocking): reconcile 652 → 1,022 file count, add catalog rows for PDFEditor + ESignatureField + RoleGate, fix Map dual-tracking (DA3-3, DA3-4).
2. **Disposition audit** (blocking): all 240 `Accepted-risk M1` items audited for true intent (DA3-9).
3. **Fix verification** (mechanical): re-run DA-1 + DA-4 fixes; verify SHA enforcement OR amend Round 1 disposition (DA3-1, DA3-6).
4. **Round 3 delta scan** (deferred OK): adversarial pass on +362 files added since Round 2 baseline (DA3-5).

The structural model holds. The tracking machinery around it does not, at this scale.

## Footnote on this review's limits

This Round 3 was scoped to **structural re-examination** and sampled 10 components across categories + 5 alias contracts + 4 late-additions. It is **not** a file-by-file pass on the +362 delta since Round 2. Findings are sufficient for a structural verdict and to identify the catalog/disposition rot but do not enumerate per-file issues in the new files. A follow-on "Round 3 delta" pass (one perspective per ~100-file batch) is recommended before any further authoring waves — and certainly before promoting the catalog to a `v1.1.0` version. Until then, the verdict from Round 1 sampling extends implicitly to today's corpus on the structural axis only.
