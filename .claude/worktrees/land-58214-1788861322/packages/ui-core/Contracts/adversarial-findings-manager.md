# Adversarial Review — The Manager Perspective
Date: 2026-06-05

## Summary
Effort allocation is broadly correct — critical/v1 components (Button, DataGrid, Dialog, Form, TextField) have substantially denser contracts than future-wave chart specs. However, two problems undercut the value of the investment: (1) a systemic metadata rot across at least 231 files where `app-priority` and `library-scope` fields are swapped or collapsed, making contracts untrustworthy as self-describing artifacts; (2) two critical/v1 components (TextBox, NumericTextBox) received the same shallow treatment as future-wave specs when they should have gotten the full reverse-spec depth given to DataGrid, Dialog, and Button.

---

## Findings

| Finding ID | Severity | Component(s) | Description | Suggested Fix |
|---|---|---|---|---|
| MG-1 | High | TextBox (#134, `critical/v1`) | TextBox Semantic is 50 lines — the same depth as a future-wave chart. It omits the props table, edge cases, deferred-features section, open-questions section, and Definition of Done gate. Contrast: DataGrid Semantic is 275 lines, Button is 319, Form is 267. TextBox is the canonical text input primitive that every form field builds on; a 50-line spec is insufficient. Additionally, all three TextBox contracts carry `#133 TextBox (app-priority: high, library-scope: planned)` in their metadata — wrong on all three fields. Catalog shows `#134, critical, v1`. | Expand TextBox Semantic to reverse-spec depth: full props table with defaults and semantics, `onBlur`/`onFocus` gap documentation, `type` restrictions, `clearButton`/`showReveal` edge-case coverage, deferred features section, open questions, and DoD gate. Correct catalog row reference to `#134, critical, v1` in all four contracts. |
| MG-2 | High | NumericTextBox (#90, `high/v1`) | NumericTextBox Semantic is 68 lines and NumericTextBox Interaction is 50 lines — both at chart-tier depth for a high-priority v1 component. Missing: props table with defaults column, controlled/uncontrolled model description, i18n/locale considerations (the `format` prop uses hardcoded `'en-US'`), edge cases (what happens when `min > max`? when `step` is fractional and `decimals=0`?), deferred features, open questions, and DoD gate. The contract also carries the metadata error `app-priority: v1` rather than `high`. | Expand both Semantic and Interaction to high-priority depth. Document the locale hardcoding as a Known Gap. Add edge-case coverage for the spinner-disable conditions and the `raw`/`editing` internal state model. Add DoD gate. Correct metadata to `app-priority: high, library-scope: v1`. |
| MG-3 | High | Fleet-wide (231+ files) | Systemic metadata corruption: `app-priority` and `library-scope` fields in contract frontmatter are frequently swapped or conflated — using scope vocabulary (`v1`, `planned`, `future-wave`) for `app-priority`, or omitting `library-scope` entirely. Confirmed instances include DropDownList (claims `app-priority: v1`), NumericTextBox (claims `app-priority: v1`), Input (claims `library-scope: planned` — should be `v1`), TextBox (claims `#133, high, planned` — should be `#134, critical, v1`), Switch (claims `app-priority: v1`), DateRangePicker (claims `app-priority: v1`), Upload (claims `app-priority: v1`), TimePicker (claims `#134`). A grep shows at least 231 files with `app-priority: v1`, `planned`, or `future-wave`. The two fields have distinct meanings per the catalog column legend (`app-priority` = ERP urgency vocabulary; `library-scope` = release-tier vocabulary); conflating them makes contracts unreliable as triage documents. | Run a grep sweep for `app-priority: v1\|app-priority: planned\|app-priority: future-wave` across all contract files. For each hit, cross-reference the catalog and correct both fields. This is mechanical enough for a Sonnet subagent pass. Block before any contracts-based tooling (e.g., a priority-aware spec linter or release-gate check) is built on top of this metadata. |
| MG-4 | Medium | Future-wave chart family (AreaChart, BubbleChart, BarChart, SankeyChart, ColumnChart, etc.) | All future-wave chart components have received four full contracts each (Semantic + Interaction + Accessibility + Styling), at 40–80 lines per contract. This is appropriate in depth — the specs are clearly forward-spec, light, and labeled as such. The concern is volume: ~30 future-wave DataVisualization components each authored at the same density as components that won't ship for multiple waves. The spec effort here is proportionate *per file* but the decision to produce all four contracts for every future-wave chart is worth questioning — a single "forward-spec note" file per chart family (Area/Bar/Bubble/Column/Range family; Gauge family; Radar family) would have captured the same design intent at 1/4 the file count. | Not a correctness fix — a scope retrospective question. For any future forward-spec batches on `future-wave` or `deferred` components, consider a single consolidated Semantic-only forward-spec per family rather than four separate contracts. Reduces the file volume by ~75% for non-implementable specs while preserving the intent. |
| MG-5 | Medium | TextBox (#134 `critical/v1`) vs TextField (also maps to `#134 critical/v1`) | Two separate four-contract families exist for what appear to be the same component: `TextBox.{Semantic,Interaction,Accessibility,Styling}` and `TextField.{Semantic,Interaction,Accessibility,Styling}`. TextField.Semantic explicitly claims "Catalog rows: #134 TextBox / #72 Input" and describes itself as the canonical single-line text input. TextBox.Semantic describes a higher-level wrapper adding clear/reveal buttons on top of `Input`. The catalog has exactly one entry for `#134 TextBox (critical/v1)`. This creates ambiguity: is TextField the implementation of catalog #134, or is TextBox? The Semantic contracts describe different components (TextBox = thin wrapper over Input with extras; TextField = the reverse-spec'd controlled wrapper). A developer consulting the catalog cannot tell which contract applies. | Clarify the relationship in both contracts' headers. If TextField is the canonical implementation of catalog #134 TextBox, rename it or cross-reference explicitly. If they are genuinely separate components, add a distinct catalog entry for TextField. The current state — two families both claiming partial ownership of catalog #134 — will cause spec-to-implementation confusion. |
| MG-6 | Low | Button (`critical/v1`) | Button Semantic is labeled `Phase M2 (forward-spec; component not yet implemented)` despite being the most thoroughly authored contract in the library (319 lines, 8 sections, full prop table, variant semantics, open questions, DoD gate). This is the right approach for a critical primitive — the effort level is correct. The concern is the phase label: if Button is forward-spec (not yet implemented), then several other contracts that reference "the Button component" (Dialog footer, ConfirmDialog, EmptyState CTA) are also implicitly forward-spec but don't say so. A reviewer skimming contracts could not determine which components are shipping vs. aspirational without cross-checking the Phase line. | No depth change needed — Button's spec effort is appropriate. Suggested fix: add a fleet-level convention document or catalog column indicating whether each contract is reverse-spec (implemented) or forward-spec (not yet implemented), so a reviewer can determine spec-to-ship status without reading each file's Phase line. |
| MG-7 | Low | Out-of-scope stubs (DataQuery, Ripple, AnimationContainer, DateMath, Diagram, ExcelExport, FileSaver, KeyboardNavigation, MediaQuery — 9 files) | All nine out-of-scope stubs are well-calibrated: each is exactly 1 paragraph that names the component, explains why it's out-of-scope, and points to the recommended alternative. This is correct and intentional. The only minor concern is that they carry `Status: Accepted` — for stubs that are permanent out-of-scope decisions, `Status: Accepted` is fine; but if any of these decisions were reversed, the "accepted stub" status creates no differentiation from an accepted full contract. | No action required on depth — effort is right-sized. Optional: consider `Status: Accepted (permanent exclusion)` to distinguish permanent out-of-scope stubs from accepted implementation contracts. |
