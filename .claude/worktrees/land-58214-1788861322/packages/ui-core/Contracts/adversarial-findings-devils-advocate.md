# Adversarial Review — Devil's Advocate Perspective
Date: 2026-06-05
Plan: idempotent-dazzling-bee.md (Phase 5)
Reviewer perspective: Devil's Advocate

## Summary

The 4-contract model (Semantic + Interaction + Accessibility + Styling) holds well for interactive components across DataEntry, Overlays, Navigation, and AI categories, where the four dimensions carry meaningfully distinct content. It degrades into thin near-empty files for the read-only display component family (all 26 DataVisualization components, the 4 gauge variants) where Interaction reduces to a single "display only + animation timing" sentence, and for alias/redirect entries where 3 of 4 contract files say only "identical to X — see X.md". At scale, this produces approximately 50–70 files that are structurally required but semantically hollow, which creates maintenance liability without proportional value. One structural gap exists: the AI components (AIPrompt, Chat, InlineAIPrompt) have a stateful streaming protocol that spans all four contracts without a coherent home, creating a risk that implementors reconstruct the parent ↔ component contract from scattered sections.

## Findings

| Finding ID | Severity | Component(s) | Description | Suggested Fix |
|---|---|---|---|---|
| DA-1 | High | ColumnChart, DonutChart, RadialGauge, RadarColumnChart + 6 other alias-derivative charts | **Alias redirect contracts are structurally hollow.** 3 of 4 contract files say only "Identical to X — see X.md." with zero additional content. This creates a 12-file per alias-pair maintenance burden: if BarChart.Interaction changes, ColumnChart.Interaction.md silently diverges from the cross-reference without any automatic enforcement. There is no spec in the system that says "if the canonical changes, the alias redirect must be updated." Divergence is the default outcome over time. | Add a versioning anchor to alias redirects: `Aliases-canonical-version: <hash or date>`. Or collapse alias redirect files to a single stub file per alias (e.g. `ColumnChart.Contracts.md` with one-line redirects for all 4 types). Either enforces the "identical to parent" claim as an explicit assertion rather than a silent assumption. |
| DA-2 | High | CircularGauge, LinearGauge, ArcGauge, RadialGauge + all read-only chart Interaction contracts (BarChart, AreaChart, LineChart, WaterfallChart, PieChart, BubbleChart, etc.) | **Read-only display components: Interaction contracts carry near-zero content.** For display-only components, the Interaction contract is 1–3 sentences: "read-only, value changes animate (N ms ease)." This is not a behavioral contract — it is a single-sentence animation spec. The animation timing (600ms vs 400ms vs 150ms) is the only differentiating content, and animation timing is arguably a Styling concern (CSS transition duration). Result: ~20–25 Interaction contract files that a new implementor would find indistinguishable from empty stubs, yet they count as "full 4-contract coverage." | For read-only display components, either: (a) merge the animation behavior into the Styling contract (where CSS transition duration lives), and allow the Interaction contract to serve as a minimal "display-only declaration" (1 paragraph max — no 4-section template required); or (b) explicitly classify these as "Display" components in the catalog and adopt a 3-contract model (Semantic + Accessibility + Styling) for them. Option (b) requires an ADR amendment; option (a) is a spec-authoring convention change only. |
| DA-3 | Medium | CircularGauge, LinearGauge, ArcGauge, RadialGauge | **Read-only gauge Interaction and Accessibility contracts are near-identical in content coverage.** CircularGauge.Interaction: "display only, 600ms animation." CircularGauge.Accessibility: "role=meter, aria-valuenow, SVG aria-hidden, G-CGAUGE-A1." LinearGauge.Interaction: "display only, 400ms animation." This imbalance means the 4-contract model here does not provide 4 equal-weight spec dimensions — it provides 3 meaningful + 1 nearly-empty. Not a merge candidate (the ARIA spec is genuinely distinct) but the Interaction contract is a structural stub dressed as a full contract. | Accept as low-content Interaction contracts explicitly — add a one-line declaration at the top of each gauge Interaction contract: `This component is display-only. | DA-4 | Medium | ColumnChart (and all 4-contract alias derivatives: DonutChart, RadialGauge, RadarColumnChart) | **Alias contracts partially diverge from "identical to" claim at the moment of authoring.** DonutChart.Interaction §2 ("center label on hover") and DonutChart.Styling §2 ("center label positioning") contain DonutChart-specific content NOT present in PieChart.Interaction or PieChart.Styling — meaning DonutChart is NOT "identical to PieChart" in 2 of its 4 contracts. This is correct and appropriate, but the header of DonutChart.Interaction §1 says "Identical to PieChart" and then §2 adds unique behavior. A future implementor who reads only §1 and stops will miss the unique content. The cross-reference pattern is inconsistent: some alias contracts say "identical" for the full contract, while others say "identical" in §1 and then add unique sections. | Standardize the alias pattern: when a contract has both shared and unique sections, replace "Identical to X" with "Extends X: all behaviors in X.Interaction.md apply except where overridden below." This makes the extension relationship explicit and eliminates the silent-stop risk. |
| DA-5 | Medium | AIPrompt, Chat, InlineAIPrompt | **AI streaming protocol lacks a coherent home in the 4-contract model.** The parent ↔ component streaming contract — who calls what, in what order, with what state transitions — is scattered across Semantic §4-5 (state enum), Interaction §3-4 (visual feedback), and Accessibility §2-3 (live-region announcements). No single contract says "this is the complete streaming integration contract." A new implementor must read all four contracts, triangulate the scattered pieces, and mentally reconstruct the streaming state machine. For 3 future-wave / low-priority components this is acceptable. But if any AI component is promoted to `planned` or `v1`, a 5th contract type ("Integration Contract" or "Events Contract") becomes warranted to consolidate: state machine transitions, parent callback signatures, error recovery protocol, cancellation semantics. | Flag this as a gap to address at promotion time: when any AI component moves to `planned` scope, add a §5 "Streaming integration note" to the Semantic contract that explicitly cross-references all three other contracts for the streaming protocol, and lists the complete state transitions in one place. This is not a 5th contract file — it is a structural cross-reference section in the Semantic contract. If Chat is ever promoted to `v1`, consider a full Integration Contract. |
| DA-6 | Medium | Tour / GuidedWalkthrough | **Tour is miscategorized: Utility folder, but Overlays semantics.** The catalog taxonomy defines Utility as "animation, drag/sortable, keyboard nav, ripple, export helpers, icons, typography — cross-cutting infrastructure" and Overlays as "dialogs, drawers, sheets, popovers, tooltips, context menus — floating / layer-above-content UI." Placing it in `Utility/` alongside out-of-scope infrastructure stubs (Ripple, AnimationContainer, MediaQuery) creates a category that mixes two fundamentally different things: pure infrastructure with no UI (Ripple, DateMath) and a fully-specified interactive overlay component. | Move Tour contracts to `Overlays/` folder to match the catalog taxonomy. This is a file move only — no content changes required. Update catalog and contract headers. The Utility category then becomes exclusively infrastructure stubs and non-UI helpers. |

| DA-8 | Low | AreaChart, BubbleChart, LineChart, RangeAreaChart, AreaSeries, LineSeries prop interfaces | **Styling properties embedded in Semantic prop interfaces.** Several chart Semantic contracts include `strokeWidth`, `fillOpacity`, `dot?: boolean`, `smooth?: boolean` as props defined in the Semantic contract's TypeScript interface. These are visual styling properties (stroke thickness, fill transparency, curve smoothness, point rendering) that belong in the Styling contract's token surface or in a `chartTheme` prop. Embedding them in Semantic couples the prop surface to presentational concerns — a violation of the 4-contract model's own separation principle. For non-chart components (Chip, Button), `variant` and `size` are in Semantic as semantic props, which is correct. The chart case is different: `strokeWidth: number` is a CSS value masquerading as a data model prop. | Move visual chart series props (`strokeWidth`, `fillOpacity`, `dot`, `smooth`, `barRadius`) out of the Semantic prop interface and into a `ChartTheme` / `SeriesStyle` type that belongs in the Styling contract. Keep data-binding props (`dataKey`, `stacked`, `name`) in Semantic. This preserves the 4-contract separation and makes the styling surface explicit. |
| DA-9 | Low | All out-of-scope stubs | **Out-of-scope stubs are well-formed but the KeyboardNavigation stub may need an implementor warning.** KeyboardNavigation.Semantic.md correctly explains that roving tabIndex is handled inline per-component. Sub-components (Error, Hint, FloatingLabel) need only Semantic (for the prop surface) + Styling (for the visual treatment). Interaction and Accessibility contracts would be trivially empty ("inherits from parent FormField") for these components. |

## Structural Verdict

The 4-contract model is structurally sound for its intended scope: interactive components with separable behavioral, accessibility, and visual dimensions. It breaks down in three specific situations:

1. **Read-only display components** — Interaction contracts become 1–3 sentences. This is a model mismatch, not a spec quality problem. Acceptable at scale only if the "thin Interaction" pattern is made explicit rather than appearing as accidentally incomplete.

2. **Alias/variant derivatives** — The "identical to X" redirect pattern works initially but creates silent divergence risk at scale. The model needs a versioning or explicit-extension convention to remain valid as parent contracts evolve.

3. **AI streaming components** — The stateless component pattern (parent owns state, component owns rendering) distributes the integration contract across all four files. The 4-contract model has no slot for "integration protocol." This is a gap to address at promotion time, not a structural flaw requiring an ADR amendment today.

None of these findings rise to the plan's kill trigger ("adversarial review uncovers that the 4-contract model itself is structurally flawed"). The model is salvageable with authoring conventions (DA-1, DA-3, DA-4, DA-5) and two targeted file moves/fixes (DA-6, DA-7). No ADR amendment required before continuing authoring.
